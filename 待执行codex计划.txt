核心修正点：
不要让服务器直接拿 Unity world 射线去和 ArUco 坐标系下的 AABB 相交。必须统一坐标系。
推荐方案：Unity 端在上传前，把食指起点、方向、终点全部从 Unity world 转成当前 ArUco-local 坐标；服务器只接收并计算 ArUco-local 射线与 ArUco-local AABB 的相交。这样历史模型、当前 HoloLens 会话、服务器查询全部对齐到同一个 marker 坐标系。

数据设计：
新增数据库表，建议命名为 `model_bounds`。表至少包含：
1. `id`
2. `task_id`
3. `status`
   - `pending`
   - `ready`
   - `failed`
   - `pending_reference`
4. `uploaded_at`
5. `model_name`
6. `fbx_name`
7. `coordinate_space`
   - 固定写 `aruco`
8. `aruco_reference_task_id` 或能追踪到参考 marker 的字段
9. `object_aruco_json`
   - 保存模型相对 ArUco 的位姿，方便之后复查
10. `aabb_min_aruco_json`
    - 例如 `[x, y, z]`
11. `aabb_max_aruco_json`
    - 例如 `[x, y, z]`
12. `corners_aruco_json`
    - 8 个角点，主要给 Unity 调试显示使用
13. `source_model_path`
14. `error_message`
15. `created_at`
16. `updated_at`

注意 AABB 的定义：
1. 这里要的是 ArUco 坐标轴对齐包围盒，也就是在 ArUco-local 空间里计算所有顶点的 min/max。
2. 不是随模型旋转的 OBB。
3. 8 个角点应由 min/max 派生出来，而不是直接保存某个旋转后局部包围盒的 8 点当作 AABB。
4. 查询用 min/max；corners 只用于调试显示和人工检查。

包围盒计算阶段：
1. 在生成流水线中新建一个阶段，例如 `bounds` 或 `model_bounds`。
2. 阶段执行时机建议在：
   - `aruco_sync` 已完成；
   - `runtime_mesh` 已完成；
   - `blender` 或最终 FBX/OBJ 输出已稳定；
   - 服务器知道 Unity 之后实际会加载哪个模型文件。
3. 如果最终显示模型来自 runtime mesh 后再转 FBX，则包围盒应基于该最终显示模型计算，避免和 Unity 实际看到的模型不一致。
4. 计算方式：
   - 读取最终模型顶点；
   - 把顶点从模型局部坐标变换到 ArUco-local 坐标；
   - 对所有 ArUco-local 顶点取 min/max；
   - 写入 `model_bounds`。
5. 如果任务没有有效 `object_aruco` 或 ArUco reference 不可用：
   - 不要写成 `ready`；
   - 写成 `pending_reference` 或跳过，之后由重建/同步逻辑补算。
6. 只有状态为 `ready` 的包围盒可以参与射线检索。

并发和锁：
1. 查询历史包围盒不需要 worker，应该是同步 DB read，避免用户交互延迟。
2. 包围盒计算和 ArUco 同步/补算可以走 worker。
3. 不建议只靠 Python 内存锁，因为服务器重启、多进程或未来迁移时会失效。
4. 推荐用数据库状态和短事务：
   - 几何计算在事务外做；
   - 最后 upsert `model_bounds` 时用短事务；
   - 查询只读 `status = ready` 的行。
5. SQLite 读写并发建议开启或保持 WAL 模式；如果当前已有统一 DB 初始化逻辑，就在那里处理。
6. 如果 ArUco reference 更新发生在模型生成期间：
   - 生成中的模型先不要被查询命中；
   - 标记 `pending`；
   - 等 `object_aruco` 和最终模型都准备好后一次性写 `ready`。

服务器 API：
新增以下接口，命名可按项目现有风格调整，但语义必须清晰：
1. `GET /model-bounds/latest?limit=5`
   - 返回最新 N 个 `ready` 包围盒。
   - 用于 Unity 调试开关显示。
   - 默认 limit 为 5。
2. `GET /model-bounds/range?start=...&end=...`
   - 返回某个上传时间范围内的 `ready` 包围盒。
   - 先实现好，Unity 端可以暂时不接入口。
3. `POST /spatial-query/ray`
   - 默认最新 5 个模型内查询。
   - 请求体包含 ArUco-local 的 `origin`、`direction`、可选 `end`、可选 `max_distance`。
   - 如果没有 end，默认最大距离 10m。
   - 返回射线路径上第一个命中的模型。
4. `POST /spatial-query/ray-range`
   - 时间范围版本。
   - 可以先实现服务端，Unity 端留函数或入口。

`POST /spatial-query/ray` 请求体建议：
{
  "origin_aruco": [x, y, z],
  "direction_aruco": [x, y, z],
  "end_aruco": [x, y, z] 或 null,
  "max_distance_m": 10.0,
  "limit": 5
}

返回体建议：
{
  "success": true,
  "hit": true,
  "model": {
    "task_id": "...",
    "model_name": "...",
    "uploaded_at": "...",
    "hit_distance_m": 1.23,
    "hit_point_aruco": [x, y, z],
    "aabb_min_aruco": [x, y, z],
    "aabb_max_aruco": [x, y, z],
    "corners_aruco": [[...], ...],
    "download_urls": {...}
  }
}

无命中时：
{
  "success": true,
  "hit": false,
  "candidates_checked": 5
}

射线与 AABB 相交算法：
1. 使用标准 slab ray-AABB intersection。
2. direction 必须归一化；服务器端仍应防御性归一化一次。
3. 处理 direction 某轴接近 0 的情况。
4. `t` 范围为 `0 <= t <= max_distance`。
5. 如果射线起点已经在盒子内部，也算命中，距离为 0。
6. 多个模型命中时，返回 `t` 最小的一个。
7. 如果 Unity 上传了 endpoint，则 max_distance 应由 `distance(origin, endpoint)` 得到，并和 10m 默认上限取更合理的截止值。

手指射线建议：
1. 用 MRTK hand joint 获取食指关节。
2. 起点建议使用 `IndexTip`。
3. 方向建议使用 `IndexDistalJoint -> IndexTip`，比直接使用某个 joint 的 forward 更容易控制和排查。
4. 如果目标手当前未被追踪：
   - 不发送请求；
   - 返回清晰日志；
   - 保持射线隐藏或显示为无效状态。

现实终点：
1. 使用 Unity `Physics.Raycast` 从食指起点沿方向打到 Spatial Awareness/空间网格对应 layer。
2. 命中则 endpoint 为 hit.point。
3. 没命中则 endpoint 为 `origin + direction * maxDistance`。
4. 调试包围盒必须放在不参与 raycast 的 layer，避免射线打到自己画出来的历史盒子。

Unity 坐标转换：
1. Unity world -> ArUco-local 的转换必须和 `RuntimeModelManager.cs` 当前 ArUco 放置逻辑互为逆变换。
2. 已知模型显示逻辑近似为：
   - `worldPosition = arucoPosition + arucoRotation * objectArucoPosition`
   - `worldRotation = arucoRotation * objectArucoRotation`
3. 因此上传前应做：
   - `originAruco = Quaternion.Inverse(arucoRotation) * (originWorld - arucoPosition)`
   - `directionAruco = Quaternion.Inverse(arucoRotation) * directionWorld`
   - `endAruco = Quaternion.Inverse(arucoRotation) * (endWorld - arucoPosition)`
4. direction 转换后再次 Normalize。
5. 不要混用 Unity world 和服务器 object_world。

【给我的操作和验收提示】

这个功能的目标不是“在屏幕上随便点一个历史模型”，而是：
我在现实空间里用手指指向一个位置，系统根据当前 ArUco 统一坐标系，查历史里哪些模型曾经在这条射线路径上，然后显示最先被指到的那个历史模型。

最关键的验收点：
1. 坐标必须统一。
   - 服务器存的是 ArUco-local AABB。
   - Unity 上传的射线也必须是 ArUco-local。
   - 如果 Unity world ray 直接上传给服务器算，就容易出现位置漂移或命中错误。
2. AABB 必须跟最终显示模型一致。
   - 如果 Unity 最终显示的是 runtime mesh 后转出的 FBX，那么包围盒就要基于这个最终 FBX 或等价模型算。
   - 不要基于旧 OBJ 算出一个和实际显示模型略有差异的盒子。
3. 只查询 `ready` 的包围盒。
   - 生成中、ArUco 同步未完成、包围盒计算失败的模型都不应该被命中。
4. 默认只查最新 5 个。
   - 这符合当前需求，也能避免历史太多导致误命中和性能问题。
5. 调试包围盒开关必须可靠。
   - 开：下载并显示最新范围内所有盒子。
   - 关：清干净，不能留下线框对象。

我需要准备或确认的东西：
1. Unity 场景里是否已经有 MRTK hand tracking 能正常读到左右手食指。
2. Spatial Awareness/空间网格是否开启，并且现实障碍物有 collider/layer 可以被 `Physics.Raycast` 命中。
3. 当前 ArUco marker 在 Unity 端是否能持续提供 `arucoPosition` 和 `arucoRotation`。
4. 服务器是否已经重启，确保新 DB 表和新 API 生效。
5. 历史 completed 任务里是否至少有几个带有效 ArUco pose 的模型，否则 latest 5 bounds 可能为空。

Unity 挂载时我要做的事：
1. 找到当前负责运行时模型和服务器请求的 manager GameObject。
2. 把新的空间历史查询脚本挂上去。
3. 在 Inspector 里设置：
   - 固定手：右手或左手；
   - 等待时间：3 秒；
   - 最大距离：10 米；
   - spatial mesh 的 LayerMask；
   - 服务器地址；
   - debug bounds 线框材质；
   - 引用 RuntimeModelManager / ShuJuQingQiu / LoadModel 或让脚本自动查找。
4. 把 `TriggerSpatialHistoryQuery()` 绑定到一个按钮、语音命令或调试按键。
5. 把 `ToggleBoundsDebug()` 绑定到另一个按钮或调试按键。

测试顺序：
1. 先不测手指，先测服务器。
   - 打开服务器。
   - 确认 `/model-bounds/latest?limit=5` 能返回历史 bounds。
   - 如果没有返回，先检查历史任务是否有 ArUco 同步结果。
2. 再测 Unity 调试盒子。
   - 在 Unity/HoloLens 中打开 bounds debug。
   - 看线框是否出现在历史模型应在的位置。
   - 关闭 debug，确认全部消失。
3. 再测手指射线。
   - 指向一个明确会穿过盒子的位置。
   - 触发查询后保持手指稳定 3 秒。
   - 看服务器是否返回命中。
4. 最后测模型显示。
   - 命中后看 Unity 是否显示对应历史模型。
   - 检查显示位置是否和 debug 盒子、现实位置一致。

异常现象和对应判断：
1. debug 盒子整体位置偏了：
   - 优先怀疑 ArUco reference 或 Unity world -> ArUco-local 逆变换。
2. 盒子跟模型方向不一致但位置大致对：
   - 检查 AABB 是不是按 ArUco 坐标轴对齐，这是正常的；AABB 不会跟模型一起旋转。
3. 手指明明指到了却不命中：
   - 检查上传的是不是 ArUco-local ray。
   - 检查 direction 是否 normalize。
   - 检查 endpoint/max distance 是否太短。
   - 检查 latest 5 里是否包含目标模型。
4. 总是命中错误模型：
   - 检查是否按最近 hit distance 排序。
   - 检查射线是否从手指正确方向发出。
   - 检查 debug bounds 是否挡住了 raycast layer。
5. 没有 endpoint：
   - 检查 spatial mesh collider 和 LayerMask。
   - 没有现实障碍物命中时，应该自动使用 10m。
6. 查询结果为空：
   - 可能最近模型没有 `ready` bounds。
   - 可能 ArUco 同步没完成。
   - 可能服务器还没跑 bounds backfill。

我对最终结果的期望：
1. 服务器有稳定的 `model_bounds` 表。
